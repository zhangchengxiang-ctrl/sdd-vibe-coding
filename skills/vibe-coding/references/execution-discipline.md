# 执行层纪律（最小充分证据）

> **从属规格层，不是第二真源。**  
> 规格 / 路由 / 回填：`SYSTEM.md` §2.1 · `vibe-coding` 主文 · [`handoff.md`](./handoff.md) · 仓内 `docs/`。  
> 本节只约束：普通修复或已挂载 `specs/<id>/` 后，如何用最少流程获得足够证据。

核心：证据优先，但证据必须服务于当前验收条件。禁止把工具次数、reviewer 数量或全仓绿灯当作质量本身。

---

## 1. 何时启用

| 档位 | 执行层 |
|------|--------|
| **Trivial / 纯 docs** | 一次编辑 + 一次确定性检查 |
| **Small fix** | 最小复现或定向测试 + 实现 + 定向复验 |
| **Non-trivial** | 按可交付 Phase 实现；每个 Phase 一次相关验证 |
| **Major / 单向门** | 用户批准计划；主代理实现；关键边界一次独立审查 |
| **Hotfix lane** | 诊断 → 最小修复 → 定向验证 → 部署；24h 内补质量事件 |

前置闸门（未满足 → **禁止**进入执行层）：

1. 已挂载 `docs/specs/<id>/`（或 small 挂在已有 spec 的 task）
2. 本次 task/Phase 的验收条件明确；无需为尚未实施的后续 Phase 填满所有矩阵
3. Major：用户已明确批准计划（只批一次）

---

## 1.1 审批与审查

自上而下，**下层不重复要上层那种「再聊一次批准」**：

| 层 | 何时 | 谁 | 挡住什么 |
|----|------|-----|----------|
| **L0 Plan Approval** | Major / AGENTS 要求的聊天计划 | 用户一句批准 | 未批 → 不进执行层 |
| **L1 直接自检** | 每个可交付 Phase 后 | 主代理对照验收条件和 diff | 相关验证未过 → 不交付 |
| **L2 独立审查** | 仅单向门、高风险或用户明确要求 | 一次 reviewer / 人审 | 具体 blocker 未关闭 → 不交付 |

L0 已批后不重复请求批准。低风险任务不自动派 reviewer；独立审查默认最多一次。

---

## 2. 默认循环

```text
1. 对齐当前 Phase 的验收条件
2. 获取最小失败证据（适合自动化时写测试；不强制为机械改动造测试）
3. 最小实现；禁止顺手扩 scope
4. 跑直接相关的检查/测试；前端行为变化做一次浏览器验收
5. 检查 diff 与验收条件；必要时更新 Spec 状态
6. 到用户要求或 Spec 约定的边界再 commit
```

定向验证通过且代码未变化后，不得重复运行同一验证。全量套件只在变更横跨全局合同、发布前、CI 要求或用户明确要求时运行。

### 团队阶段门

Spec 用 `Delivery Target` 声明本轮交付终点，用 `Current Gate` 声明当前团队阶段：

| Gate | 通过条件 | 失败回流 |
|------|----------|----------|
| **shape** | 目标、首个价值切片、关键假设可由产品专家判断 | 继续 Ground / Shape |
| **ready** | 当前切片 SC 可执行；环境、账号、数据与依赖可用 | blocked，不进入实现 |
| **build** | 垂直切片代码已集成，非分层半成品 | 返回 build |
| **verify** | `testing` 选择的直接正确性证据通过 | 返回 build |
| **demo** | 目标用户通过真实生效通道办成事；UI 用 宿主约定的浏览器验收（见 AGENTS.md） | 实现偏差→build；设计问题→shape |
| **deliver** | 达到 `code-ready` / `dev-effective` / `production-delivered` 约定 | 返回 deliver 或 rollback |
| **observe** | 运行结果和产品反馈已进入当前 Spec / remediation / 下一切片 | 补证据或分类反馈 |

`Done` 只能表示达到声明的 Delivery Target；`code-ready` 不得冒充 `dev-effective`，
`dev-effective` 不得冒充 `production-delivered`。产品专家判断用户价值，体系负责所有
内部规格、测试和交付证据。

### Requirements Lock 与打扰预算

Shape 阶段允许与产品专家集中讨论，体系先调查内部事实和必要互联网信息，再用带推荐
的 Decision Card 澄清高价值问题。当前 Slice 的问题框定、关键取舍、交付目标和
Scenario 确认后，`Requirements Lock=locked`。

锁定后的默认行为是自主执行。只有以下情况可中断用户：

- **Agent 无法代劳**的外部动作（见下节「身份切换」）——不是「需要某个角色」本身
- 新发现单向门、破坏性操作或不可逆产品决策
- 运行证据与锁定合同冲突，且会实质改变用户结果
- 无法通过仓库、工具或安全默认解除的真实 blocker

其他可逆实现细节由 Parent 决定；非阻断问题批量放入下一次 Demo / Decision Card。
若用户主动改变目标，显式设 `Requirements Lock=reopened`，回到 shape，不在 build
中偷偷漂移需求。

### 身份切换 vs 真实等人（防把能做的推给用户）

复发：Browser 验收撞到「非 Admin / 非目标角色」→ 立刻 Decision「请你登录」→ 用户反问
「你为什么自己登不了」。根因是把「需要某身份」误写成「必须用户完成的登录」。

| 情况 | 正确动作 |
|------|----------|
| 本地账号密码登录可用（登录页有用户名/密码） | **自己** logout → 密码登录目标账号 → 继续测 |
| 仓库 / 前次会话 / E2E helper 有可复用测试凭据 | 先搜再用；口令过期则换已知新口令或查 DB/文档，**禁止**未试就等人 |
| E2E / 脚本可注入 token（`auth-token` / JWT helper）且验收合同允许 | 可用脚本换身份；勿因此改产品态造假冒充 Browser 合同 |
| 第三方一键登录 / SSO 扫码、用户个人 OAuth、生产密钥、必须「真人本人」的角色 | 才登记 **等人队列**；陈述缺什么，不写成「要不要我继续」 |

开口前自检：

1. 缺的是**权限/角色**，还是真的缺**人类器官**（扫码、私密密钥、本人）？
2. 有没有先打开登录页 / `LoginForm` / 搜测试账号？
3. 若下一句是「请你登录 Admin」——删掉，改成自助换号；仅当上表末行成立才中断。

**禁止**：把「第三方登录走不了」与「密码登录能走」捆成同一个硬 blocker；禁止用 Decision Card
掩盖未做的自助登录尝试。

### 子代理编排合同

**定位**：子代理是受控的上下文隔离器，不是默认虚拟团队。Parent 始终负责目标、
架构决策、最终写入整合和完成判断。

只有以下条件**全部满足**才派发：任务可独立描述；输入/输出边界明确；结果可用
证据验收；并行或独立视角收益明显高于交接成本。否则 Parent 直接完成。

| 类型 | 默认权限 | 适用 |
|------|----------|------|
| Explorer | 只读 | 不同领域的调用链、现状与风险调查 |
| Writer | 明确且不重叠的文件集 | 合同已确定的独立模块或机械修改 |
| Tester | 测试文件或只读运行 | 长而独立的场景验证 |
| Reviewer | 只读 | 单向门、安全或关键公共合同 |

每次派发的最小上下文包必须包含：**目标、已知事实、边界、权威真源、不变量、
明确不做、允许修改文件、输出格式、证据要求、停止条件**。返回只保留：
**结论、证据、未确认项、越界/未检查、建议动作、实际修改/验证**；禁止把探索
流水账倒回主上下文。

预算与并发：

- 默认 **0 个**；跨独立领域调查最多 2–3 个只读 Explorer。
- 并行读、串行决策；共享工作树可有多个不相交 Writer，但同一文件/代码区域同时只允许一个 Writer。
- Tester 与 Reviewer 通常二选一；单向门/高风险最多一次独立只读审查。
- 禁止 reviewer → 修复 → reviewer 循环；具体问题由 Parent 修复并定向复验。
- 禁止通用 Writer 自主闭环 DB、权限、Git、迁移或 进程 / 部署单元边界（见宿主 AGENTS.md）。
- 不为派发新建 `subagent-plan.md`；必要的执行说明只在对应 task 下写一行。

Parent 只吸收可验证事实、关键路径、明确风险与未决冲突。多个结果冲突时回到
代码或运行证据，只补查冲突点，不按多数投票，也不再派“全面复核”代理。

重量级 / 多日 spec 仍使用 `.claim` 契约，但 **不得因此自动创建 worktree**。只有用户在当前对话明确要求 worktree 时才允许创建；否则留在当前工作树并按 Spec 路径隔离修改。仅同一行、同一生成产物或同一运行时资源发生真实冲突时停下说明 blocker。

### 熔断

- 调查 10 分钟内必须产生有效 diff、明确结论或真实 blocker。
- 同一区域第 2 次修复仍失败 → 停止补丁叠加，重新诊断并决定重写/回退。
- 全量测试出现无关失败 → 确认一次归因，记录后退出；不得扩 scope。

## 3. 与规格层的边界（冲突检查表）

| 若想做… | 正确落点 | 错误落点 |
|---------|----------|----------|
| 产品设计 / 方案 | `design` → `product/modules/` | 另存第二套设计真源 |
| 开版本 / 切版 | `spec` → `docs/specs/<id>/` | 会话 plan 文件冒充版本包 |
| 任务进度 | `specs/<id>/tasks.md` | 聊天 checklist / 第二份 plan.md |
| 发版 / reload | 宿主 AGENTS.md 中的部署命令 | 非正式发版习俗 |
| 跨会话路由 | `handoff.md` + `.claim` | 仅靠 worktree 分支名 |
| 完成定义 | 用户明确目标生效 + 直接验收条件 | 「全仓绿了 / reviewer 数够了」 |

双仪式自检：同一决策是否出现在**两处互不等价**的真源？若是 → **删执行层那份**，只留 `docs/`。

---

## 4. Verification before completion

宣称「完成 / 可合并 / 已修复」前（对齐 vibe-coding §5 + 完成门禁规则）：

1. 当前 diff 引入或直接相关的失败已解决
2. 直接验收条件有可指认证据
3. 前端用户可见行为已走仓内 宿主约定的浏览器验收（见 AGENTS.md）（若适用）
4. 已挂载 Spec 的状态确实变化时才回填 / 更新 handoff / 删 claim
5. 无关失败已明确归因，未被偷偷吞入范围

最小充分证据优先于仪式和自称。
